# gongoozler: architecture and code review, 3 Nov 2026

**Scope:** the uncommitted working tree of 3 Nov 2026:
- the Python library (`python/src/gongoozler`, 1,016 lines);
- the Go CLI (`cmd/`, `internal/`, 1,500 lines);
- the specs, plan and kb.

**Method:**
- I read every source file.
- I ran `make check` and `go test -race ./...`.
- I wrote 12 reproductions for suspected defects; every finding below marked "reproduced" was
  observed, not inferred. The scripts and commands are in [repro/](repro/README.md).
- Timings are medians of three on Ashley's Omarchy machine, where differences under about 5% are
  noise.

**The standard:** it was reviewed as a production system for running and watching quantitative
simulations: something people will trust with long, expensive runs, and later run at scale.

## Verdict

The core semantics are right, and better tested than most systems at this stage. The weaknesses
are around them:
- the edges of the telemetry pipeline;
- process supervision;
- the data path.

**What is strong:**
- **The merge reproduces Nautilus exactly.** Streaming feeds in windows replays exactly what adding
  each feed whole replays: proven by 200 randomised cases, and on real Nautilus with 5,000+ tied
  timestamps, timers included. That is the hardest property in the system, and it holds.
- **The streaming architecture is cheap.** A window costs about 3.6 µs of Nautilus overhead
  (reproduced: 16,676 windows, no slower than one run). The worry that sparse feeds would
  fragment dense ones into slow windows is unfounded.
- **The design instincts are sound:**
  - never block the run on I/O;
  - count every drop;
  - report how a run ended from outside it;
  - take the peak from the kernel (`ru_maxrss`);
  - write normative specs;
  - back every performance claim with a script.

**What is not yet acceptable:**
- **Three defects are critical, because each one silently destroys the record of a run.**
  - One `NaN` passed to `emit()` erases all of a run's events, while the run reports `ok` (C1).
  - One large log line ends the event stream for the rest of the run (C2).
  - Killing the CLI leaves the run running unsupervised, with no events stored and listed as
    `running` forever (C3).
- **Supervision leaks.**
  - Child processes outlive their run (H1).
  - Signals reach the run twice through uv (H2).
  - Memory is overcounted 4× for fork-based runs (H3). Memory is the reason a run is ever sent to
    a box, so that number has to be right.
- **"Never block the run" holds for I/O, but not for CPU.** The sender thread serialises JSON
  under Python's global lock, and steals it from the strategy: 67% at high event rates (H4).
- **A backtest platform must keep its results, and this one keeps none.** No fills, positions,
  account history or returns are persisted, and there is no record of what data a run saw (H5).
- **The data path runs through per-item Python objects.** Building them costs as much as the
  simulation. Nautilus's own Parquet catalog, streamed in Rust, does a run about 2× cheaper with
  bounded memory (H6).

None of this needs a redesign. It needs the supervisor and the data path finished properly
before anything is put in a box.

### C1: one non-finite number destroys the run's whole record

**Where:** `_events.py:284`. `flush()` calls `json.dumps(…, allow_nan=False)` outside the
`try` that guards `sink.write` (lines 290–295).
- `_finite()` sanitises only the top-level `done`, `total`, `rate`, `eta` and `value` arguments.
  Everything passed through `emit()`, `params()` or nested values is unchecked.
- A tuple used as a dict key raises the same way.

**Reproduced:** `gz.emit("custom", value=float("nan"))`:
- The sender thread died with `ValueError: Out of range float values are not JSON compliant: nan`.
- No events from the run reached the CLI, not even `hello` or the log line emitted before the
  bad event. They shared its batch.
- Everything afterwards went nowhere: the thread is gone.
- The CLI recorded `status: ok`. The only trace is a traceback in the run's stderr.

**Why it matters:** NaN is an ordinary value in quantitative code: a Sharpe ratio on flat
returns, a missing price. The failure is total and silent, the opposite of the protocol's
"nothing is lost silently".

**Fix:**
1. Serialise each event in its own `try`. On failure, sanitise and retry, or replace the event
   with a `telemetry` record of what was dropped and why. One event may be lost; never a batch,
   never the thread.
2. Make the sanitiser recursive: non-finite numbers become `null`; anything else falls back to
   `str`.
3. Wrap the sender loop so that it cannot die: catch `BaseException`, count it, and continue.
4. A test per case: NaN, infinity, an unencodable key, a recursive object.

### C2: one large line ends the stream

**Where:**
- `internal/local/local.go:324–339`: `bufio.Scanner` with a 4 MiB limit.
- Python sends any size (`_events.py:104`).

`bufio.Scanner` stops for good at a line over its limit. The connection is closed, Python's
next `sendall` fails, the emitter marks the sink dead (`_events.py:295`), and everything after is
dropped. Those drops can no longer reach the CLI. The comment on `read` says "never fatal"; it
is fatal.

**Reproduced:** `gz.log("x" * 5_000_000)` (a DataFrame's repr will do it):
- received: `hello`, `before`, `cli.protocol: bufio.Scanner: token too long`, then nothing;
- the later log and stage were lost;
- `run.end` still said `ok`, with `protocol_errors: 0` (M8).

**Fix:**
- **In Python:** cap each field (64 KiB for `msg`, say) and each event (1 MiB), truncating with
  a marker and counting.
- **In Go:** read with `bufio.Reader`. Skip a line over the limit up to its newline, count it,
  and keep reading.
- **Tests:** a 5 MB line followed by a normal one must deliver the normal one.

### C3: a dead CLI leaves an unsupervised run

**Where:** `local.go:179`. `Setpgid: true` takes the run out of the terminal's foreground group
(rightly, for signal control), but:
- there is no `Pdeathsig`;
- no `SIGHUP` handling;
- nothing records that the run is supervised.

**Reproduced:** after `kill -9` of the CLI:
- the run kept going, with parent PID 1, in its own group;
- its events had nowhere to go;
- the run directory held 0 events (M3: nothing had been flushed yet);
- `gongoozler ls` lists it as `running`, with no file name, forever.

Closing the terminal should do the same, by the same mechanism: the CLI gets `SIGHUP`, and the
run, in a group of its own, does not. That was not reproduced.

**Why it matters:** this is the classic way a long backtest leaks: a laptop lid shut, an SSH
session dropped. In a box (slice 2) it means a run billing CPU with nothing watching it.

**Fix:**
- `SysProcAttr.Pdeathsig = SIGTERM` on the child (Linux). The kernel then signals the run when
  the CLI's thread dies (lock the launching goroutine to its OS thread).
- Handle `SIGHUP` like `SIGTERM`.
- Write `meta.json` at the start, with `status: running`, the CLI's PID and its start time.
  `ls` then reports `lost` when that process is gone. Remove stale sockets on start.

### H1: processes outlive their run

**Where:** `local.go:223–255`. After `cmd.Wait()` the group is never signalled, so anything the
run started is left running: pool workers, a local cluster, a helper.

**Reproduced:** a run started `sleep 41` and exited. The CLI exited 0, and `sleep 41` was still
running, with parent PID 1, in the run's group.

**Fix:** the supervisor owns the tree.
1. Become a child subreaper (`prctl(PR_SET_CHILD_SUBREAPER)`), so orphans come back to the CLI to
   be reaped and counted.
2. At the end, send `SIGTERM` to the group, then `SIGKILL` after a grace period. Report what had
   to be killed.
3. **Test:** the group is empty when `run` returns.

In boxes, `tini` or the container runtime does this, but the local CLI needs it itself.

### H2: signals arrive twice under uv

**Where:** `local.go:215` sends to the whole group (`kill(-pgid, sig)`), and uv forwards SIGINT
and SIGTERM to its own child.

**Reproduced:** one SIGTERM to the CLI, and the run's handler recorded
`['SIGTERM', 'SIGTERM']`. SIGINT did the same.

**Why it matters:** a common pattern is "first Ctrl-C: flush and stop cleanly; second: abort".
Here the first Ctrl-C aborts, and cleanup in `finally` blocks is interrupted halfway, so
half-written outputs get kept.

**Fix:**
- Send the first signal to the group leader only (`cmd.Process.Signal`): uv forwards it. A
  launcher that does not forward gets a flag.
- Escalate to `SIGKILL` on the whole group after a grace period, or on the second signal.
- **Test:** the run sees exactly one signal.

### H3: memory is overcounted for forked workers

**Where:** `procmem.go:25–50` sums RSS across the group. RSS counts every resident page a process
maps, shared pages included, so N workers sharing a parent's memory copy-on-write count it N+1
times. `ru_maxrss` is right for one process, but not for a tree.

**Reproduced:** three forked workers over a 200 MB array:
- summed PSS, the true figure: 197 MiB;
- reported peak: 788.3 MiB.

**Why it matters:** placement ("publish when the header asks for more than this machine has")
and box sizing rest on this number. A 4× error sends runs to boxes they don't need, or sizes
boxes four times too big. Multiprocessing is the normal way to parallelise sweeps in Python, so
this is the common case, not the corner.

**Fix:** measure memory where the kernel accounts it.
- **Best:** run each run in its own cgroup and read `memory.current`, `memory.peak` and
  `memory.events` (`oom_kill`). That is also the exact out-of-memory signal, replacing the
  SIGKILL heuristic.
  - Locally: `systemd-run --user --scope -p MemoryMax=…`, where systemd runs (it does in WSL when
    enabled).
  - In boxes: the container's own cgroup.
- **Fallback:** sum PSS from `/proc/PID/smaps_rollup`, which costs more, so sample less often.
- Never sum RSS.

### H4: telemetry costs the strategy CPU

**Where:**
- `_events.py:272–295`: serialisation runs in the run's own interpreter, on the sender thread,
  under the GIL;
- `_events.py:228`: ordered events have no rate limit (only logs do).

**Reproduced:**
- **Throughput:** 300,000 `emit()` calls in 0.47 s. 90,659 (30%) were dropped and counted. End to
  end, the sender and the CLI drained about 200,000 events a second; the 100,000-event buffer
  absorbed the rest until it filled.
- **Contention:** a CPU-bound loop with one event per 100 iterations took 0.275 s, against
  0.134 s for the loop and 0.052 s for the calls themselves: 67% that only the sender's GIL time
  explains.

At control-plane rates (under 1,000 a second) the cost is negligible. But nothing keeps a user at
those rates, and the people most likely to emit per fill or per tick are the ones running the
largest simulations.

**Fix:**
- **Now:**
  - rate-limit ordered events per kind, like logs, with drops counted;
  - document the boundary: events are for the control plane, and domain data goes in columnar
    artifacts (H5).
- **Next:** take serialisation off the interpreter. The run writes small fixed binary records into
  a shared-memory ring buffer: single producer, single consumer, mmap'd, sequence-numbered. The
  supervisor drains it and encodes JSON for the world.
  - Writing a record is a few hundred nanoseconds, with no allocation, and no lock beyond the
    producer's own.
  - The reader is out of process, so it takes no GIL.
  - It survives the run dying: whatever was written is readable afterwards. That fixes "the last
    events before a crash" for free.
  - This is the standard low-latency telemetry design (the LMAX Disruptor, Aeron, Chronicle).
    Done in Rust behind PyO3, it can be shared with fi-engine's progress counters.

### H5: a backtest platform that keeps no results

**Where:** `nautilus.py` streams the run and stops. Its only outputs are wall-clock-sampled
metrics (M5). Nautilus already produces everything a results store needs, and none of it is
kept:
- `BacktestNode.generate_orders_report`, `generate_order_fills_report`,
  `generate_positions_report` and `generate_account_report`;
- `BacktestResult.stats_pnls`, `stats_returns`, `stats_general` and `returns_series`.

Nor is the input recorded:
- `run.start` holds the file's hash and the lock's hash (if a lock exists: unlocked files run
  unpinned, silently);
- nothing records what data the feeds delivered.

**Why it matters:**
- Two runs cannot be compared.
- A rerun cannot be checked.
- A result cannot be audited.
- The run page the design describes has nothing to show.

For a quantitative platform this is the product, not a feature.

**Fix:**
1. **The driver writes results as artifacts:**
   - Nautilus's reports as Parquet;
   - the returns series and statistics as Parquet and JSON;
   - the tearsheet from `create_tearsheet_from_stats`.
2. **A run manifest:**
   - the file hash, and a lock (made on first run if absent, as the design already says);
   - the resolved versions;
   - the Nautilus version;
   - the engine configuration and parameters;
   - and, per feed: name, item count, first and last `ts_init`, and a rolling hash of the
     timestamps (plus selected columns when they are columnar).
3. **Reruns compare results, not logs.** Event logs depend on wall clock and are never
   reproducible.

### H6: the data path is Python objects

**Where:** the feed contract (`feeds.py`) is sequences of Python objects. Checking reads every
`ts_init` in Python: 51 ms per million, plus 19 ms to check order.

**Measured (e12):** 1,000,000 quotes, Nautilus's EMA cross, like engines on both sides:

| Path | Per run |
| --- | ---: |
| Building the quotes as Python objects | 1.01 s, before the run |
| `gongoozler.nautilus.run` over those objects | 1.05 s |
| Writing them once to Nautilus's `ParquetDataCatalog` | 0.65 s, once |
| `BacktestNode` streaming the catalog, decoded in Rust | 0.97 s, reading and decoding included |

The orders were identical (3,281). Every box in a sweep builds its objects again, so per run the
catalog path is about 2× cheaper: 0.97 s against 2.06 s. Its memory is bounded by Nautilus's
chunks, against every object held. Nautilus 2.0's Python API has Arrow encoders for market data
(`quotes_to_arrow_record_batch_bytes`) but no decoders, so the catalog is the columnar way in.

**Fix:** make the catalog a first-class kind of feed.
1. **`CatalogFeed`:** a data library writes once in Nautilus's schema (`write_quote_ticks`,
   `write_bars`, … or Arrow). Many runs read it. That is pull-once-run-many, with no design of our
   own.
2. **`gongoozler.nautilus.run_node`:** drives `BacktestNode`, with progress from the in-loop actor
   (about 1,000 timer events per run: measured within noise).
3. **Keep the object feed** for small and custom data. Validate columnar timestamps vectorised
   (Arrow/numpy: about 1 ms per million), not per item.

### M1: the merge is quadratic on long same-timestamp bursts

**Where:** `feeds.py:225`. Extending a buffer concatenates what is left with the new batch. When
one timestamp spans many batches, the "nothing below the bound" path (lines 269–273) extends the
same buffer again and again.

**Reproduced:** the cost per item grows with the burst: 240 → 450 → 790 → 1,250 ns as the burst
doubles. 1,000,000 same-timestamp items take 1.25 s to merge. Normal data never does this (e8),
but a snapshot load or a fine-grained library will.

**Fix:** buffer as a deque of chunks with a cursor. Cut by bisecting each chunk's timestamps, and
copy only what is emitted.

### M2: the live view slows the run when it prints

**Where:** `term.go:205–212`. Every printed line erases and redraws the status block, and output
is rendered on the goroutine that drains the run's pipe (`local.go:342`), under the renderer's
lock.

**Reproduced:** 100,000 printed lines:
- 0.24 s bare;
- 0.28 s plain;
- 0.96 s live, writing 12.6 MB to the terminal: 10× the output.

A full pipe blocks the run's `print`.

**Fix:**
- **Separate storing from showing.** Storing is a fast path that never waits on a terminal.
  Showing is a separate stage that coalesces: print accumulated lines, then redraw the block at
  most 10 times a second.
- In JSON mode, buffer stdout (one write per event today).

### M3: what a crash loses

**Where:** `events.go:147`. The log flushes only on an append at least 0.5 s after the last
flush. Resource events every second keep the window near a second, but:
- a CLI killed in its first second stores nothing (C3's run: 0 events);
- `meta.json` exists only for runs that ended;
- the socket file stays behind (`defer os.Remove`).

**Fix:**
- Flush on a 100 ms ticker, and at once on stage, error and artifact events.
- `fsync` at the end.
- `meta.json` at the start (C3).
- Remove stale sockets on start.

### M4: the test suite's own defects

- **A data race in a test.** `TestAnInterruptReachesTheRunAndIsReported`
  (`cmd/gongoozler/main_test.go:144`) reads a `bytes.Buffer` while `os/exec` writes to it. Use a
  locked writer, or poll the run's event log.
- **A flaky test.** `TestARunsEventsAreStoredInTheOrderTheyHappened` asserts that a stdout line
  arrives before a stderr line. Two pipes have no order between them, and it failed under
  `-race`. Assert order within each stream.
- **`make check` does not run `-race`.** It should, every time.

### M5: metrics on the wall clock

**Where:** `nautilus.py:81`. Snapshots follow `every_s` of wall time, so how often the equity
curve is sampled depends on how fast the machine is. That is fine for a live gauge. It is wrong
for anything kept, compared or plotted as a result.

**Fix:**
- Live metrics stay wall-throttled, and are labelled live.
- Kept series come from the simulation: Nautilus's own returns series and reports (H5), or
  snapshots on a simulated-time grid.

### M6: `artifact()` blocks the run

**Where:** `_events.py:459–475`. The file is hashed and copied on the caller's thread: seconds
for a large Parquet file.

**Fix:** the run declares a path; the supervisor, out of process, hashes and copies it, or
hard-links it on the same filesystem. Only then is the artifact event final.

### M7: the feed contract has gaps a quantitative user will hit

- **No look-ahead guard.** A Nautilus item known before it happened (`ts_init < ts_event`) is a
  look-ahead bug in the data library. It is cheap to check, and only a check catches it.
- **No declaration of instruments and data types.** An unregistered instrument fails deep inside
  Nautilus, mid-run, instead of at the start.
- **No identity.** No fingerprint, count or vintage, so H5's manifest has nothing to record.
- **No data revisions.** fi-engine's whole design is point-in-time with vintages. A feed that
  cannot carry a revision cannot reproduce a corrected run.

### M8: `ok` with telemetry lost

**Where:** `run.end` reports the process's exit status only. A run whose event stream died (C1,
C2) or that dropped events (H4) says `ok`.

**Fix:** add `telemetry: complete | partial` to `run.end` and `meta.json`, with the drop and
error counts. Count scanner errors in `protocol_errors`. Show "ok, telemetry incomplete" when it
applies.

### M9: permissions

**Where:** run directories are 0755, and `events.jsonl` and `output.log` are 0644
(`local.go:88`, `events.go:127`). A run's output can hold anything its data library printed.

**Fix:** 0700 and 0600, as for the socket's directory.

### Low

- **L1:** the signal goroutine never ends (`local.go:209`): `signal.Stop` does not close the
  channel. Harmless in the CLI, a leak once the server reuses `local.Run`.
- **L2:** an exit code of 137 from the user's own `sys.exit(137)` is reported as SIGKILL, with
  the out-of-memory note (`local.go:291`). A cgroup's `oom_kill` count (H3) makes this exact.
- **L3:** `events.Decode` accepts trailing data after the object.
- **L4:** `hello` records `argv`, and arguments are where people put tokens. Make it opt-in, or
  redact.
- **L5:** the version is in three places (`pyproject.toml`, `__init__.py`, `main.go`). The CLI
  and library never compare builds, only the protocol.
- **L6:** the code carries `# noqa` and `# type: ignore` comments for tools the repo does not
  run. There is no CI, no ruff, mypy or golangci-lint, and no fuzzing.
- **L7:** the "last stage begun" note can name a stage that had already ended before the failure;
  report the innermost stage still open.
- **L8:** `events --follow`, `attach`, `kill RUN` and a working `ls` status are missing: the CLI
  cannot watch a run it did not start.

## How it becomes great

Six shifts. Each is a principle from low-latency systems that this codebase already half
follows.

### 1. Keep Python off the hot path, both ways

Python should orchestrate, not touch rows.
- **In:** data comes in columnar (Nautilus catalogs; Arrow), H6.
- **Out:** results go out columnar (Parquet reports and series), H5.
- **Telemetry:** control-plane events only, cheap and bounded (H4). Domain data never goes
  through the event stream.

### 2. Make telemetry a lock-free ring, read out of process

- The run writes fixed-size records into a shared-memory ring buffer.
- The supervisor drains it and speaks JSON and SSE to the world.
- The run never allocates or serialises for telemetry, never contends for its GIL, and loses
  nothing when it crashes: the ring outlives it.
- The same ring carries fi-engine's Rust counters.

This replaces the sender thread and its failure modes (C1, H4, M3) in one move.

### 3. Make the supervisor the source of truth

One process owns:
- the run's process tree (subreaper, death signal, group cleanup);
- its accounting (cgroup memory, CPU and out-of-memory kills);
- its durability (a log flushed on a ticker, `meta.json` from the start);
- its artifacts (hashed and copied out of process).

The local CLI and slice 2's box agent are the same code, so everything proven here holds in a
box. Today the run reports more about itself than its supervisor does, and that is backwards.

### 4. Results are data, and reproducibility is checked on results

- Every run persists Nautilus's reports, the returns series and the statistics.
- Every run has a manifest of its inputs, with feed fingerprints and a lock.
- A rerun checks itself against result hashes. That is the product a quantitative team buys:
  "show me what this run did, and prove this rerun did the same".

### 5. Separate simulated time from wall time

- **Two series:**
  - deterministic series on a simulated-time grid, which are kept and comparable;
  - wall-clock telemetry, live and disposable.
- **Sweeps run locally first:** across a machine's cores, in parallel processes, with core and
  memory limits. Boxes come only after that. It is the cheapest scale-up there is, and it uses
  the same supervisor.

### 6. Budgets enforced by CI, not by prose

The specs make promises. Make them build failures:

| Budget | Bound |
| --- | --- |
| Telemetry overhead, default settings, on a Rust-native strategy | ≤ 1% |
| Silent loss | Zero. Every drop counted and surfaced in `run.end` |
| Orphans | Zero: the process group is empty when `run` returns |
| Supervisor death | The run is ended within 1 s, and the run directory marked `lost` |
| Memory | Within 5% of the cgroup's figure, or summed PSS |
| Event latency, local, end to end | p99 under 250 ms |
| Ingest through a catalog | ≥ 1M quotes a second a core, and growing with Nautilus |

`tools/spikes` already holds most of these measurements. Wire them into `make bench` with
thresholds, and run them with `go test -race`, ruff, mypy and golangci-lint in CI.

| D: the fast path (two to three weeks) | H6 (`CatalogFeed`, `run_node`, vectorised checks). H4 next: the ring buffer, in Rust, shared with fi-engine. Local sweeps across cores | The budgets table holds in CI |
| E: boxes (slice 2) | The same supervisor as the box agent, with container cgroups, leased jobs and content-addressed artifacts | Slice 2's evidence, on a supervisor already proven locally |

Doing D before E matters. Building boxes on today's supervisor would ship C3, H1 and H3 into
every container, where they cost money instead of a laptop's patience.

**The six shifts:**
1. **Python off the hot path:** catalog feeds streamed in Rust; timestamps handed over as arrays
   and checked vectorised; results written once, at the end.
2. **The ring**, read out of process. Its format is language-neutral, for fi-engine's Rust loops
   to write in slice 4. The review imagined the ring itself in Rust; the writer is Python's
   `struct` into an `mmap`, measured at 2 µs a progress update, inside the budget.
3. **The supervisor as the source of truth** ([../spec/supervisor.md](../spec/supervisor.md)).
4. **Results as data**, with `diff` and `rerun`.
5. **Simulated time apart from wall time,** and local sweeps across cores (`gongoozler sweep`,
   ranked by a statistic).
6. **Budgets enforced by CI** (`make bench`, in the workflow).

**Phase E, boxes:** `gongoozler server` and `gongoozler worker`, the same supervisor in each box,
the container's cgroup, leased jobs with heartbeats, expiry and retry, content-addressed blobs
([../spec/server.md](../spec/server.md)). A file gives byte-identical results here and through a
worker (`TestAFileRunOnTheServerKeepsTheSameResultsAsHere`). The Docker launcher is tested against
a fake Engine API: Docker is not available to this machine's user, so `make e2e-docker` runs in
CI, not here.
